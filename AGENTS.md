# Conventions de code pour les assistants

Ces règles s’appliquent aux assistants de programmation qui modifient Glimio. Avant un changement, lire les documents pertinents : [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) pour les frontières, [`docs/FRONTEND.md`](docs/FRONTEND.md) pour Angular et Tailwind, [`CONTRIBUTING.md`](CONTRIBUTING.md) pour les validations et [`docs/RELEASING.md`](docs/RELEASING.md) pour les versions.

## Frontières et structure

- Garder l’application Python (`src/seance` et `src/web`) indépendante du client web (`src/web/frontend`). Le cœur et les providers Python ne doivent importer ni Angular ni FastAPI; le frontend ne dépend que de l’API HTTP/SSE.
- Respecter les sous-paquets existants (`seance/media`, `seance/processing`, `seance/providers`). Placer chaque nouvelle responsabilité dans la couche qui la possède; éviter les modules de compatibilité et les réexports ajoutés uniquement pour préserver un ancien chemin d’import.
- Intégrer les moteurs IA et outils remplaçables derrière les contrats et fabriques de providers. Garder leurs options, formats, arguments, détection de disponibilité et détails d’exécution dans l’adaptateur correspondant. Exposer au frontend les capacités, options et états par les contrats API génériques; ne pas coder les noms de moteurs ou leurs options en dur dans Angular.
- Les traitements et événements métier restent dans le cœur Python. La couche Web les adapte à l’API et au flux SSE; le frontend réutilise le service d’événements partagé au lieu d’ajouter du polling pour suivre les traitements.
- Pour l’ETA, conserver les horodatages et l’historique des phases sur les jobs. Les estimations doivent se recalculer à partir de la phase active et des durées réellement observées, avec un repli sur l’historique total pour les anciens jobs qui n’ont pas ces données. Ne pas prétendre connaître un pourcentage de progression si le provider ne le fournit pas.
- Les fermetures de flux SSE causées par un client déconnecté sont attendues : toujours désinscrire le client dans un `finally`, traiter uniquement les erreurs de connexion usuelles sans masquer les autres erreurs, et laisser les annulations asyncio se propager.
- Ne pas ajouter de dépendance à un outil externe sans en documenter la raison, l’installation, la version et la licence. FFmpeg est requis pour les conversions média qui le nécessitent; les autres moteurs doivent rester échangeables via leurs providers.

## Python

- Suivre le style et les motifs des modules voisins. Garder les types métier et contrats indépendants des frameworks; typer les nouvelles frontières publiques et convertir les erreurs propres aux moteurs en erreurs de domaine compréhensibles.
- Garder l’orchestration, la persistance et les règles métier dans les use cases. Un provider s’occupe de communiquer avec son moteur et de traduire ses entrées, options, événements et résultats vers les types Glimio.
- Éviter les appels bloquants dans les handlers asynchrones de l’API. Pour les longues tâches, utiliser le système de jobs existant et publier des événements compatibles avec le suivi SSE.

## Angular 22, Tailwind CSS 4.3.3 et styles

- Conserver la séparation des composants en fichiers `.ts`, `.html` et `.scss`, ainsi que l’organisation par fonctionnalités sous `src/web/frontend/src/app/pages` et les éléments communs sous `src/web/frontend/src/app/shared`.
- Réutiliser les composants, services, contrôles, jetons et styles partagés existants avant d’en créer de nouveaux. Utiliser `glimio-icon` avec les Heroicons enregistrées; ne pas intégrer de SVG d’icône à la main.
- Pour les champs communs, `.field-label` est l’unique source de vérité pour l’espacement label/contrôle : sa marge basse partagée est `mb-2` (8 px). Les notes `.field-note` utilisent la marge haute partagée `mt-2`. Les wrappers d’un champ label + contrôle ne doivent pas remplacer cet espacement par `gap-*` combiné à des marges remises à zéro ; garder leur grille sans gap vertical et laisser les marges partagées faire le travail. Éviter les sélecteurs trop larges comme `.common-processing-fields > div { gap-* }` qui écrasent le rythme des colonnes de champs ; appliquer le gap aux groupes identifiés (`.processing-basics`, `.processing-extras`, `.session-processing-column`) plutôt qu’à chaque `div`. Cette règle s’applique aussi aux champs dynamiques (`provider-option`) et aux contrôles composés comme la traduction du résumé : regrouper les contrôles d’un même champ dans un wrapper sans gap, puis réserver le gap du parent à la séparation entre champs ou entre champ et action. Les composants encapsulés, notamment `glimio-checkbox-field`, ne doivent pas redéfinir localement `m-0`, `mb-*` ou le `line-height` du titre lorsqu’ils portent aussi `.field-label`. Réserver les exceptions (libellé masqué, rangée compacte ou label contenant une sortie sur la même ligne) à des sélecteurs ciblés et justifiés. Après tout changement, comparer label/contrôle checkbox, input et select dans les formulaires standard, les réglages et les options de séance.
- Toute chaîne visible doit utiliser le système de traduction existant (`interface-language.service.ts`) et être fournie dans toutes les langues prises en charge.
- Dans un SCSS de composant, importer les utilitaires Tailwind avec `@reference` vers `src/web/frontend/src/styles/tailwind-ref.scss`. Toute propriété CSS standard ayant un utilitaire Tailwind équivalent DOIT passer par `@apply` (dimensions, espacements, display, alignement, couleurs, bordures, positionnement, typographie, visibilité, etc.) ; ne pas écrire la même règle en CSS brut par préférence ou pour gagner une ligne. Exemple : utiliser `@apply border-l-3 border-l-danger` au lieu de `border-left: 3px solid var(--c-danger)`. Les propriétés à base de valeurs de thème/compositions (`color-mix()`, ombres de marque, animations et transitions précises) doivent, quand elles sont réutilisées ou sémantiques, être déclarées comme jetons dans `tokens.scss` et `tailwind.css`, puis consommées par un utilitaire (`bg-danger-banner`, `bg-success-soft`, `border-danger-border`, `shadow-danger-halo`, etc.). Ne pas répéter un même `color-mix()` dans plusieurs feuilles de composants. Ne garder une déclaration CSS directe que si aucun utilitaire ni jeton partagé ne couvre fidèlement le besoin, ou pour une exception documentée de cascade/structure (par exemple une exception de cascade documentée).
- Limiter fortement les utilitaires Tailwind à valeur arbitraire (`h-[84px]`, `text-[13px]`, `grid-cols-[...]`, etc.). Avant d’en ajouter, chercher un utilitaire de l’échelle existante ou un jeton partagé. Pour une dimension précise qui fait réellement partie de la mise en page, préférer une propriété CSS structurelle lisible ou un jeton sémantique partagé (par exemple les largeurs de la navigation et la largeur maximale du contenu) plutôt qu’une valeur arbitraire dispersée. Ne pas remplacer artificiellement une classe entre crochets par une valeur numérique exotique uniquement pour la masquer ; conserver les exceptions seulement si la précision est nécessaire, éviter les doublons de valeurs et expliquer le besoin lorsqu’il n’est pas évident.
- Toute classe Tailwind sémantique personnalisée utilisée avec `@apply` doit être un utilitaire réellement défini dans le thème Tailwind 4. Pour les tailles typographiques (`text-*`), déclarer les tokens `--text-*` et leur interligne si nécessaire dans `src/styles/tokens.scss` (résolution de `@apply` via `tailwind-ref.scss`) ainsi que dans l’entrée CSS simple `src/styles/tailwind.css` (génération des utilitaires globaux). Ne jamais introduire un nom comme `text-compact`, `text-caption` ou `text-micro` sans définir le token correspondant et valider la compilation Tailwind ; une vérification de chaînes ou des délimiteurs ne détecte pas les utilitaires inconnus.
- Le CSS natif de `modern-normalize.scss` est l’exception du reset système vendorié et doit rester entièrement dans `@layer base` : ses réinitialisations comme `button { margin: 0 }` ne doivent pas écraser `.field-label` dans `@layer components`. Les déclencheurs `<summary>` des menus définissent explicitement `grid` dans les styles partagés ; ne pas ajouter d’override hors couche tant que le reset reste dans `base`.
- Réserver `src/web/frontend/src/styles/components.scss` aux styles réellement communs. Ne pas dupliquer des styles globaux dans les pages ni recopier un composant standard pour un usage local. Vérifier le budget de style Angular avant d’ajouter beaucoup de règles à une page.
- Respecter l’accessibilité et les motifs Angular déjà utilisés : contrôles natifs, libellés associés, focus clavier visible, état accessible, responsive, signaux/RxJS et gestion du cycle de vie sans abonnement ou écouteur laissé actif.

## Modifications et vérification

- Faire des changements ciblés et préserver les modifications préexistantes. Ne supprimer un document, contrat ou chemin que si ses références et son rôle ont été vérifiés.
- Mettre à jour les traductions et la documentation quand le comportement visible, les options d’un provider, la configuration ou l’installation change. Ajouter les notes de version dans `CHANGELOG.md` quand le travail fait partie de la préparation d’une release; suivre `docs/RELEASING.md`.
- Exécuter les vérifications pertinentes décrites dans `CONTRIBUTING.md` et `docs/FRONTEND.md`; ne pas affirmer qu’une compilation ou des tests ont réussi s’ils n’ont pas été lancés.
